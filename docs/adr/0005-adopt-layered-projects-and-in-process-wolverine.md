# Adopt layered projects and in-process Wolverine

MDSweep adopts Motion's API, Application, Domain, Infrastructure, AppHost, ServiceDefaults, and Web project shape while retaining MDSweep's vertical feature ownership. Domain state and rules have no MDSweep dependencies. Application owns command/query contracts and results. Infrastructure owns EF Core, file parsing, Keycloak administration, clocks, and handlers that use those adapters. API owns the HTTP and authentication boundary.

Wolverine is approved only for in-process command/query dispatch, Wolverine HTTP endpoints, and explicit lightweight EF Core transaction middleware. Mutating handlers use `[Transactional]`; queries do not receive transaction middleware. Two workflow-preserving commands keep an explicit EF Core save instead: Driver access creation must compensate by deleting the newly created Keycloak user if the local commit fails, and assignment must translate a database uniqueness race into the existing HTTP 409 response. Neither command uses Wolverine transaction middleware. This use does not configure Wolverine PostgreSQL persistence, durable queues, inboxes, outboxes, scheduled jobs, sagas, or Wolverine-managed migrations. The existing EF Core migration chain remains authoritative for the single MDSweep application database.

The Angular application uses lazy workflow routes, Tailwind, a minimal generated Spartan control set, TanStack Query for non-persisted server state, and TanStack Table for dense Manifest and service-day tables. The existing durable Driver action queue stays separate from TanStack Query.

This decision retains the current Keycloak authorization-code BFF, HttpOnly application cookie, same-origin token-free Angular client, one Keycloak realm per environment, one MDSweep database plus a separate Keycloak database, manual MTM Manifest input, and manual MTM billing-file output. Middleware beyond Wolverine's EF unit of work, authorization redesign, email, outbox, and jobs remain outside this refactor.
